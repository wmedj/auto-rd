# AI Agent 自动研发流水线规划

## 1. 目标

这个项目的目标不是先做某个具体业务功能，而是先验证一条可复制的自动研发流程，让仓库成为 Agent 的实验场。

核心目标有三个：

1. **把任务入口标准化**：所有功能需求、缺陷、线上问题统一进入 GitHub Issue。
2. **把执行过程自动化**：通过 GitHub Actions + 大模型 Agent 自动分析、编码、提交 PR。
3. **把验收和风险控制清晰化**：由人类定义验收标准，由 CI、Reviewer Agent 或人工完成审核。

---

## 2. 角色分工

### 人类负责人

负责：

- 定义问题是否值得做
- 明确业务目标
- 编写验收标准
- 指定测试方式
- 决定是否合并

不再默认负责：

- 手工实现全部代码
- 手工处理每个低风险改动

### Builder Agent

负责：

- 读取 Issue
- 分析仓库上下文
- 进行代码修改
- 运行测试 / 检查
- 提交 PR

### Reviewer Agent（可选）

负责：

- 审核 PR 是否符合 Issue 目标
- 检查风险项
- 检查测试覆盖和验收情况
- 给出可合并 / 不可合并结论

---

## 3. 建议的流水线

```text
GitHub Issue
  -> triage / label
  -> agent-ready
  -> GitHub Actions 触发
  -> Builder Agent 拉取上下文并实施修改
  -> 提交 PR
  -> CI / Reviewer Agent / 人类审核
  -> 合并
```

### 阶段 A：任务准备

任务进入 GitHub Issue 后，必须补齐以下信息：

- 背景
- 目标
- 非目标
- 验收标准
- 测试方法
- 风险范围

只有满足这些条件，才能打上 `agent-ready` 标签。

### 阶段 B：Agent 执行

GitHub Actions 可以基于以下条件触发：

- 新 Issue 被打上 `agent-ready`
- 定时扫描 backlog 中的 `agent-ready` Issue
- 人工通过 `workflow_dispatch` 指定某个 Issue 运行

Builder Agent 收到任务后，应该执行以下步骤：

1. 读取 Issue 内容与附件。
2. 拉取仓库并分析相关文件。
3. 识别验收标准和限制条件。
4. 完成修改。
5. 运行最小必要测试。
6. 生成 PR，引用 Issue。

### 阶段 C：PR 审核

PR 审核不再只看代码“写得像不像人写的”，而是重点看：

- 是否完成 Issue 目标
- 是否符合验收标准
- 是否附带足够测试
- 是否引入越界改动
- 是否存在明显风险

---

## 4. Issue 设计原则

一个适合 Agent 执行的 Issue，必须具备以下特点：

### 必须写清楚的内容

#### 4.1 背景

说明为什么做这件事，以及当前现状。

#### 4.2 目标

只写最终结果，不写模糊动词，例如避免“优化一下”“看看能不能”。

#### 4.3 非目标

明确什么不在本次范围内，避免 Agent 过度扩展。

#### 4.4 验收标准

验收标准最好写成可判断的条目，例如：

- 当输入 A 时，返回 B
- 页面出现按钮 C
- 错误日志 D 不再出现
- 单元测试覆盖路径 E

#### 4.5 测试方法

要说明如何验证，包括：

- 手工操作步骤
- 自动化命令
- 环境约束

---

## 5. 标签设计

建议先使用最少但清晰的标签集合：

- `agent-ready`：任务描述完整，可以交给 Agent 执行
- `needs-spec`：需求不够明确，暂不执行
- `human-review-required`：必须人工审核
- `safe-task`：低风险任务，可优先交给 Agent
- `bug`：缺陷类任务
- `feature`：功能类任务
- `ops`：流程、配置、脚本类任务

---

## 6. 第一阶段适合给 Agent 的任务

为了先找手感，建议从低风险任务开始。

### 推荐优先级

#### P0：非常适合

- README / 文档完善
- Issue / PR 模板
- GitHub Actions 配置
- 小型脚本
- lint / formatting 修复

#### P1：可以尝试

- 独立模块的小功能
- 明确输入输出的接口改动
- 可回归测试的 Bug 修复

#### P2：暂时不要默认交给 Agent

- 核心鉴权
- 支付 / 计费 / 权限
- 大规模架构重构
- 缺少测试保护的核心链路

---

## 7. 验收标准模板

建议每个任务至少包含以下验收字段：

### 功能验收

- [ ] 功能行为符合描述
- [ ] 不影响已有核心流程

### 技术验收

- [ ] 修改范围可解释
- [ ] 有最小必要测试或检查
- [ ] PR 描述包含验证方式

### 风险验收

- [ ] 高风险文件未被无关修改
- [ ] 未引入不必要依赖

---

## 8. GitHub Actions 设计建议

推荐拆成三层：

### 8.1 Router Workflow

职责：监听 Issue 事件，判断是否应该唤起 Agent。

### 8.2 Builder Workflow

职责：调用实际 Agent（例如 Codex、Claude Code、其他内部 Agent）。

### 8.3 Review Workflow

职责：在 PR 创建后运行 Reviewer Agent 或规则检查。

当前仓库先提供 Router 入口骨架，后续你可以根据使用的具体大模型供应商继续接入 Builder。

---

## 9. 运行策略建议

### 模式一：手动触发

最适合刚开始练手。

- 人创建 Issue
- 人确认内容完整
- 手动运行 workflow_dispatch
- 观察 Agent 执行结果

### 模式二：标签触发

适合进入日常使用。

- 只要 Issue 被打上 `agent-ready`
- 自动唤起 Builder Agent

### 模式三：定时拉取

适合 backlog 比较稳定时。

- 定时扫描未处理的 `agent-ready` Issue
- 自动挑选低风险任务执行

建议你先从 **模式一 + 模式二** 开始，不要一上来就全自动。

---

## 10. 失败处理机制

必须预设 Agent 会失败，因此流程里要有明确回退策略。

### 常见失败

- Issue 描述不够清晰
- Agent 改动范围过大
- 测试失败
- PR 能运行但不符合真实业务意图

### 处理规则

- 若 Issue 信息不足：退回并标记 `needs-spec`
- 若 PR 偏题：关闭 PR，补充模板字段
- 若测试失败：允许 Agent 重试一次，避免无限循环
- 若连续失败：任务转人工或拆小后重试

---

## 11. 建议的迭代路线图

### 第 1 周：先打地基

- 建立 Issue / PR 模板
- 建立标签规范
- 建立 Router Workflow
- 手动挑 3 个低风险任务练手

### 第 2 周：验证闭环

- 接入一个 Builder Agent
- 让 Agent 真正提交 PR
- 梳理 PR Review 清单
- 记录失败原因

### 第 3 周：提高成功率

- 优化 Issue 模板
- 增加测试规范
- 对高频错误建立提示词或规则

### 第 4 周：引入 Reviewer Agent

- 让第二个 Agent 做 PR 审核
- 尝试对低风险任务半自动合并

---

## 12. 你现在最该做的事

如果目的是“在这个项目里找手感”，建议按下面顺序推进：

1. 用仓库模板创建第一个 `safe-task` Issue。
2. 手动触发一次 Agent 工作流。
3. 看 PR 是否真的围绕验收标准工作。
4. 记录 Agent 失败点是出在：任务描述、上下文获取、测试、还是审查。
5. 连续跑 3 到 5 个任务后，再考虑全自动。

重点不是一开始就追求完全无人值守，而是先把：

- 任务格式
- 验收标准
- 审核动作
- 失败回退

这四件事打磨清楚。
